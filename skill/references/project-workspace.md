# 项目工作区与连续修改

一个项目关联一次，记录随项目保存；每次任务按当前模型和要求提取必要上下文。上下文的依据是版本、原话与文件，不依赖某个聊天窗口是否还记得。

## 用户最短路径

在顶栏“关联项目”选择建议工程或系统文件夹。首次关联会把当前素材和已完成的记录复制到项目的 `.motion-studio/`，原工作区保持。项目已有工作区时直接打开，不覆盖。A项目切B项目时不复制A的内容。下次启动优先恢复最近可用项目。

也可由Agent直接打开已明确的工程：

```sh
node "$SKILL_DIR/scripts/start.mjs" --project "/absolute/path/game"
```

`--workspace PATH` 仍可打开独立审阅目录；已有独立目录迁入工程用 `project-open --workspace PATH --path PROJECT`。CLI默认迁入当前资料，`--empty` 只开独立项目；`start --project` 默认不带入另一个独立目录，只有显式 `--adopt-current` 才迁入。

创建采用暂存目录和最终目录提交，已有未知文件不会被覆盖。待处理/运行任务不能在首次迁移中被悄悄复制成第二份执行；已关联项目切换在另一个本机服务打开，原服务仍绑定原工作区。

已明确关联且迁到游戏目录之外的工作区，会按当前关联和本机最近项目记录直接复用。重新打开同一工程、从最近项目返回或使用 `start --project`，都不在游戏中重新创建 `.motion-studio/`。外部工作区仍能读取关联工程上下文，修改输出留在该外部目录。

## 记录结构

```text
游戏项目/
  src/、public/、制作源等原工程文件
  .motion-studio/
    project.json             各模型版本对、当前预览投影与资产身份
    catalog.json             目录索引、文件状态与扫描进度
    project-link.json        工程身份、相对根路径、可选来源映射
    assets/<SHA>.glb          原版及每个独立候选
    sources/、conversions/    导入副本、转换与可编辑源
    jobs/<任务ID>/
      job.json               状态、输入版本、父任务与用户决定
      context.json、view.png  提交现场与原话
      project-context.rN.*    每次提交/补充时冻结的工程和历史依据
      agent-output/          脚本、候选、审计与执行记录
    checkpoints/             用户明确认可的精确预览版本
    decisions/               每次决定的独立记录
```

最近项目路径保存在本机 `~/.motion-atelier/recent-projects.json`，不是项目制作数据。页面有“打开记录文件夹”和复制路径入口；用户无需显示隐藏文件。

工作区记录不等于正式游戏安装。生成候选、用户认可预览、写入游戏是三个不同事实。程序不会自动改游戏资产、提交Git或上传工程。大文件使用项目自己的备份/资产版本管理方式，复制工作区时不要丢掉JSON引用的GLB。

## 每次任务怎样取上下文

`project-context --workspace PATH --request TEXT --slot candidate` 预览，`--job ID` 读取当时冻结快照；MCP工具为 `motion_project_context`。当前任务的冻结快照应优先于新的即时预览。

选定输入SHA是检索锚点，对照槽只说明正在比较什么，不能把另一个角色的代码当本轮来源。定位顺序为实际源路径/文件SHA、制作清单和字面资产引用，再到名称/关键词候选。每项记录相对路径、SHA、来源原因、证据及摘录行号。同名、旧清单哈希不符或缺失来源会明确标候选/警告。

只读取关联工程范围；不泛扫用户目录，不运行项目脚本来获取上下文。忽略生成物、工具自身工作区与凭据文件。代码/制作源/历史参考按数量和总字数限制提取，截断会说明。当前明确导入的FBX和转换生成的Blender源可从受控来源记录中定位，即使工作区不参与泛扫。

候选保留上游制作源身份，但上游Blend/运行时文件未必已包含后续GLB微调。此时会标注“上游版本”；不能用旧制作源重新导出并覆盖已保留的改动。先重放或合并修改，再检查目标和保护范围。

## 连续修改的规则

- 父链按选定候选SHA追溯，显式parent必须匹配真实输入。跨动作版本可作来源桥，不混入另一个动作的要求。
- 历史用户要求、补充原话完整保留；明确preserve作为继承条件。此前已完成目标只作背景，不重复执行。
- AI摘要不产生新的用户约束。用户明确的新要求优先；冲突不明确时提问。分支不唯一时说明歧义，不猜合并。
- 用户认可绑定精确文件SHA，旧偏好、数值检查或“生成完成”不冒充认可。后续改口追加决定，旧检查点仍可追溯。
- 第二轮比较的是本轮输入A→输出B。拒绝当前B可恢复A；最初原版单独保留。评审历史任务不会回退当前新head。
- 新候选必须保留源文件的原有动作名称。资产版本变了或已确认代码/制作源变了，拒绝用旧任务覆盖当前候选。
- 需要补充时会生成新上下文修订，旧修订不改。普通文字补充不能静默接受期间变动的制作源；这种情况转过期并重提。

工程搬迁用相对project-link根路径恢复。旧文件的绝对地址只作为创建时记录，CLI `job` 返回的 `executionPaths` 才是当前执行入口。不要改写旧快照去伪装它始终来自新位置。

## 可选的明确来源关联

自动证据不足时，可以在工作区 `project-link.json` 的 `assetLinks` 加入精确来源映射。普通用户不必填写；Agent可在用户已明确指定来源后维护。映射不改变游戏文件。

```json
{
  "assetLinks": [{
    "asset": {"sha256": "当前模型的完整SHA-256"},
    "code": ["src/characters/hero.js"],
    "sources": ["characters/hero/source.blend"],
    "history": ["docs/hero-feedback.md"]
  }]
}
```

这些是 `project-link.json` 的附加字段，保留已有version/projectId/rootRelative等内容。只凭originalName的映射仍是候选；不要把猜测写成已确认制作链。
